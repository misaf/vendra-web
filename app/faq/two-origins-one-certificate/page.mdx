# Two origins, one certificate, and a page that looks fine

A storefront running locally spans two origins: the storefront host itself, and
the API host it fetches from. In self-signed mode both are served by a generated
local authority, and the browser will warn about both.

Accepting the warning on the page you are looking at does not cover the other
one. That is the whole bug.

## The failure looks like success

  label="What the browser actually does"
  nodes={['Server render', '200 OK', 'Browser fetch', 'TLS refused']}
/>

The page renders on the server, which already trusts the authority through
`NODE_EXTRA_CA_CERTS`. So the response is a genuine 200 with correct markup —
and every data section empty. The server logs nothing, because from its point of
view nothing failed. The requests that failed are the browser's own, visible
only in the network panel.

An empty product grid reads like a data problem. It is almost never a data
problem.

## The fix, in order

The exception persists. Certificates are re-signed from a persistent authority
at `certificates/ca.pem`, so it survives `vendra property render`, and accepting
the API origin once covers every property added later. Only deleting `ca.pem` or
the state directory invalidates it.

## Why HSTS stays off here

Under `certificate_mode: self-signed`, `TRAEFIK_HSTS_SECONDS` is `0`.

An HSTS header served with a certificate the browser does not trust pins the
host to HTTPS *and* removes the "proceed anyway" bypass. A local `.test` host
becomes unreachable until someone clears HSTS state by hand. Enabling HSTS
before real certificates exist is a self-inflicted outage.
