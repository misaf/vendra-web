# One browser origin and a server-side certificate chain

A local storefront has two network relationships, but only one browser origin.
The browser loads the storefront host and sends client reads to its same-origin
`/api/proxy/*` route. The storefront container—not the browser—connects to the
canonical API host.

That distinction determines which trust store matters.

## The two trust decisions

<Flow
  label="Request path"
  nodes={['Browser', 'Storefront origin', '/api/proxy/*', 'API origin']}
/>

The browser must accept or trust the storefront certificate. The container must
trust the API certificate authority through `NODE_EXTRA_CA_CERTS`. The
controller mounts the generated CA into the container for that server-side
relationship.

Opening `https://api.<base_domain>` in the browser is not part of normal setup
and does not repair a server-side trust failure.

## The fix, in order

<Steps
  items={[
    {
      title: 'Accept the storefront certificate',
      body: 'Open https://<slug>.<base_domain> and accept the local certificate, or trust certificates/ca.pem once at the operating-system level.'
    },
    {
      title: 'Verify the container CA mount',
      body: 'If server reads fail, inspect NODE_EXTRA_CA_CERTS and the mounted ca.pem path inside the storefront container.'
    },
    {
      title: 'Verify through the storefront origin',
      body: 'Check /api/health and /api/proxy routes without sending the browser directly to the API host.'
    }
  ]}
/>

The generated authority persists at `certificates/ca.pem`, so operating-system
trust survives property rendering. A per-host browser exception still applies
only to the storefront hostname accepted in that browser profile.

## Why HSTS stays off here

Under `certificate_mode: self-signed`, `TRAEFIK_HSTS_SECONDS` is `0`. Enabling
HSTS with an untrusted certificate removes the browser's bypass and can make a
local host unreachable until its HSTS state is cleared manually.
