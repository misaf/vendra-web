# Storefront API and tenancy

<Lede>
  All storefronts call one canonical Laravel API host, so the request host cannot
  identify a property. Everything below follows from that single constraint.
</Lede>

## Current request context

Server calls and the same-origin proxy provide:

<DefList
  items={[
    {
      term: 'Origin',
      description: 'The property’s public origin.'
    },
    {
      term: 'X-Storefront-Domain',
      description: 'Its registered tenant domain.'
    },
    {
      term: 'X-Storefront-Key',
      meta: 'optional',
      description: 'An opaque, server-only credential.'
    },
    {
      term: 'Authorization: Bearer …',
      meta: 'when present',
      description: 'A separate end-user identity, independent of the above.'
    }
  ]}
/>

The backend currently resolves the tenant from `Origin` or `Referer`, matched
against an active tenant domain. Dynamic CORS uses the same active-domain
inventory.

## Security limitation

<Callout type="error">
  `Origin`, `Referer`, and `X-Storefront-Domain` can all be forged outside a
  browser. The storefront can send `X-Storefront-Key`, but Laravel does not
  validate it yet, and the controller does not provision a credential
  automatically.
</Callout>

Treat current header-based selection as **tenant routing, not proof of tenant
identity**.
