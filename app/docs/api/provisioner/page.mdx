## Authentication

Set one long random value as `VENDRA_PROVISIONER_TOKEN` in
`/etc/vendra/controller.env`. The controller uses it to authenticate inbound
calls, and injects the same secret into the platform app as
`STOREFRONT_PROVISIONER_TOKEN`, which Laravel’s queued provisioner job sends as
its bearer token.

<Flow
  label="One secret, two names"
  nodes={[
    'VENDRA_PROVISIONER_TOKEN',

/>

<Callout type="error">
  Keep the service internal to the platform network. This credential is unrelated
  to the proposed per-storefront API credential — do not reuse one for the other.
</Callout>

## Responses and errors

<DefList
  items={[
    { term: '200', description: 'The request succeeded; a storefront response reports ready, reference, and resolved image digest.' },
    { term: '401', description: 'The bearer token is absent or does not match the provisioner token.' },
    { term: '422', description: 'The request is well-formed HTTP but violates the provisioner contract or deployment invariants.' },
    { term: 'Transport or 5xx failure', description: 'Treat as infrastructure failure. Capture provisioner logs and let Laravel own bounded retry policy.' }
  ]}
/>

Validation failures require corrected input. Do not retry the same invalid
payload indefinitely. Infrastructure failures may be retried only after
confirming the dependency is recovering and the queue will not amplify load.

<Callout type="info">
  Consult `api/openapi.yaml` in the controller repository whenever request or
  response fields change. This page intentionally describes behavior rather than
  duplicating the full schema.
</Callout>
